Paper2Proof
Software Requirements Specification
Claim level reproduction of research experiments
Version 1.0 • 26 October 2026 • Proposed implementation baseline
Purpose and product decision
Paper2Proof will help a researcher select a measurable claim from a scientific paper, construct a bounded experiment, execute it, and inspect whether the observations reproduce the reported result under documented conditions. The system will deliver source-linked claims, runnable code, measurements, assumptions, and a reproducibility package.
The hackathon MVP will support a small, curated set of CPU-friendly numerical or optimization papers. It will use existing Meta models for reasoning and code generation. It will not train a new foundation model, certify the truth of a paper, or promise reproduction of arbitrary scientific research.
Audience and authority
Prepared for Pranav D. Patel and the Paper2Proof implementation team. This document is a proposed engineering specification, not a record of completed functionality or measured performance. “Shall” denotes a release requirement. P0 is required for the MVP; P1 is optional after all P0 acceptance checks pass; P2 is a future capability.

1 Product scope and constraints
Problem and expected outcome
A paper may omit preprocessing rules, random seeds, configuration values, or hardware details. Reimplementation can therefore produce plausible but incomparable results. Paper2Proof shall make those gaps visible and separate implementation failure, environmental mismatch, and measured disagreement.

Explicit exclusions
The MVP excludes physical laboratory experiments, medical conclusions, formal theorem proving, proprietary datasets, open-ended dependency installation, arbitrary internet access from experiment code, large-model training, autonomous publication, and public multi-tenant hosting.
Supported experiment contract
A supported claim must have a measurable outcome, an available dataset or reproducible synthetic generator, a reviewed evaluation adapter, and a feasible CPU budget. Two or three papers will be selected during implementation; no particular paper is assumed supported until its data, license, method, and runtime have been checked.
An experiment using substituted data, reduced training, different hardware, or a changed baseline shall be labeled “adapted experiment.” It may demonstrate behavior, but shall not receive an unqualified reproduction verdict for the original claim.
Operating assumptions
Initial deployment is a private authenticated demo on a Linux host with at least 4 CPU cores and 16 GB RAM. Each experiment receives at most 2 CPUs and 4 GB RAM. API access, model availability, dataset rights, and final hackathon rules remain deployment prerequisites. Numeric budgets are engineering defaults and must be validated before release.

What the upstream project provides

Paper2Proof shall acknowledge that overlap and shall not claim that execution or automated repair alone is an original contribution.

Reuse requirements
LIC-01 · P0  Before copying code, record the exact upstream commit, URL, imported paths, license text, and local changes in a third-party inventory. This SRS does not claim that an upstream commit has already been integrated.
LIC-02 · P0  Preserve applicable copyright and attribution notices, distribute the Apache 2.0 license with reused material, mark modified upstream files, and retain applicable NOTICE content if present in the selected revision [S3].
LIC-03 · P0  Audit imported dependencies, papers, and datasets separately; the repository license does not establish rights to every input or model. Describe pre-existing work and new work accurately in the hackathon submission; verify the event rules before submitting.
Model creation decision
Paper2Proof is an agent application built on existing models. A single capable Meta model may serve extraction, planning, generation, and review roles with different prompts and typed outputs. Muse Code is a coding agent, not a separate model; direct Model API use is the MVP integration [S4]. Fine-tuning is deferred until a licensed dataset and a reproducible baseline justify it.
The new functionality must remain useful even if the implementation source changes. Claim specifications and evaluation evidence are therefore independent of the code-generation backend.

UC-01 · Upload  Researcher uploads a supported PDF. The system validates bytes, extracts pages, and creates claim candidates. An unreadable, encrypted, or over-limit file receives a specific error; unsupported pages are flagged.
UC-02 · Select and specify  Researcher opens a claim and sees its passage, expected value, dataset, baseline, and missing details. Editing a material assumption creates a new specification version. A run cannot start with unresolved comparability blockers.
UC-03 · Execute  Researcher starts a validated specification within a displayed budget. The UI shows planning, coding, testing, and execution events. A bounded repair loop can fix code; the result is measured by the trusted evaluator.
UC-04 · Review a discrepancy  A completed run differs from the published target. The system displays measurements, uncertainty, configuration differences, and relevant source passages. It reports “not reproduced in this run” only if comparability checks pass.
UC-05 · Handle insufficient information  The paper omits a required setting or the dataset is unavailable. The system records the blocker and returns an inconclusive assessment. The researcher can supply information or create an explicitly adapted experiment.
UC-06 · Cancel or exhaust budget  Researcher cancels, or a hard limit expires. Workers stop, partial artifacts remain, and the state indicates cancellation or budget exhaustion. No successful reproduction verdict is synthesized.
UC-07 · Export and rerun  Researcher downloads a package containing code, specification, dependency records, metrics, and provenance. An independent rerun uses the same specification; every new attempt gets its own identity.
UC-08 · Delete  Researcher deletes a project. Access is revoked immediately, active work is canceled, and project artifacts are removed according to the retention policy. A minimal content-free deletion audit remains.

4 Paper ingestion and claim requirements
FR-01 · P0  The API shall accept PDF uploads up to 25 MiB and 50 pages. It shall verify file signatures, reject corrupt or encrypted files with actionable messages, assign an ID, and calculate a SHA-256 digest.
FR-02 · P0  Extraction shall retain original page numbers, text spans, and bounding boxes where available. Text extraction and document parsing shall run as untrusted-input processing with a timeout and memory limit.
FR-03 · P0  The original PDF shall remain available in the project so users can compare extracted passages against the source. Missing text, ambiguous equations, and table-reading problems shall be visible before execution.
FR-04 · P0  The claim extractor shall emit schema-validated candidates containing the claim text, source passage, page, type, metric, unit, direction, reported value, dataset, baseline, and any conditions. Unknown fields shall be null with a reason.
FR-05 · P0  A source validator shall confirm that cited spans exist in the extracted document. An agent confidence score shall not substitute for source validation. Unresolved extraction errors shall block an affected claim.
FR-06 · P0  The feasibility check shall classify claims as supported, requires information, or out of scope. Reasons shall include unavailable data, unsupported metric, ambiguous method, excessive resources, or external equipment needs.
FR-07 · P0  The user shall be able to correct claim fields and add supplementary information. Corrections shall be attributed to the user and versioned without changing the source PDF or prior claims.
FR-08 · P0  Candidate claims shall be treated individually. A result for one claim shall never be promoted into a verdict for the entire paper. The report shall show both selected and untested claims when available.

5 Experiment specification requirements
FR-09 · P0  Each experiment shall reference one immutable claim version and one evaluator version. Its specification shall include the objective, method, baseline, dataset digest or generator, preprocessing, split, seeds, hyperparameters, metric formula, units, hardware assumptions, repetitions, and budget.
FR-10 · P0  Every nontrivial setting shall be classified as paper-specified, user-provided, or agent-assumed, with a source or rationale. Required unknown values shall remain visible and shall not be silently filled.
FR-11 · P0  A comparability checklist shall assess method fidelity, dataset and split, baseline, preprocessing, compute conditions, and metric semantics. Known material mismatches shall force adapted or inconclusive classification.
FR-12 · P0  The comparison rule, uncertainty procedure, and tolerance shall be fixed before execution. Tolerance shall come from the paper or an explicit user-approved policy with rationale. No universal accuracy or runtime tolerance shall be assumed.
FR-13 · P0  The interface shall show the complete specification and estimated cost and runtime before Start. Starting a run records acceptance of that version.
FR-14 · P0  Changes to data, baseline, metric, seed policy, tolerance, or hyperparameters after execution begins shall create a new experiment version. Results shall not be combined across versions without explicit labeling.
FR-15 · P0  Datasets shall be acquired by an approved broker, validated, checksummed, and mounted read-only. The MVP shall prefer preloaded public data or fixed synthetic generators. Downloaded archives shall be checked for traversal, symlinks, decompression limits, and declared licensing.
FR-16 · P0  The planner shall allocate budgets across implementation, tests, and repeated measurement. It shall refuse infeasible workloads before starting and shall never assume unlimited GPU or cloud access.
Definition of readiness
A specification is ready only when source references validate, mandatory fields exist, a reviewed evaluator supports the claim, data is available, all blocking assumptions are resolved, and the resource budget fits the supported profile. Assumed settings may remain for adapted experiments, but their effect on the conclusion must be explicit.
Avoiding result-driven tuning
An observed mismatch is evidence, not an instruction to optimize until the reported value is reached. Any later exploratory tuning shall be a separate labeled experiment with its full search history retained.

6 Code generation and execution requirements
FR-17 · P0  Code generation shall produce a Python project following a controlled adapter interface. The output shall contain implementation files, configuration, dependency declarations, and method-to-source notes. Generated code shall not select the final verdict.
FR-18 · P0  Dependencies shall come from an approved, pinned environment. New packages require operator review and a separately built image. Experiment code shall not install packages or download resources during evaluation.
FR-19 · P0  Validation shall include import checks, small deterministic smoke tests, input and output schema checks, and domain-specific correctness tests. Reviewer comments from an LLM are advisory and shall not replace these checks.
FR-20 · P0  The orchestrator may perform at most three repair attempts after the initial implementation. Repairs shall respond to a specific test or execution failure, preserve specification semantics, and record code diffs and diagnostics.
FR-21 · P0  The runner shall execute each attempt in an isolated, non-root environment with no host secrets, network disabled, read-only inputs, restricted syscalls, dropped capabilities, and explicit CPU, RAM, process, disk, and time limits.
FR-22 · P0  A trusted supervisor shall capture start and end time, exit code, image digest, resource use, standard output, standard error, generated outputs, and artifact digests. Model-written logs shall never be treated as trusted telemetry.
FR-23 · P0  Cancellation shall interrupt the process tree and terminate remaining processes after a grace period. Timeout, out-of-memory, disk exhaustion, malformed outputs, and security-policy violations shall have distinct reason codes.
FR-24 · P0  A fresh attempt directory shall be used for every repair and rerun. Earlier results shall be immutable. Identical Start requests with the same idempotency key shall not launch duplicate jobs.

7 Verification and verdict requirements
FR-25 · P0  Evaluation shall use a versioned, reviewed harness isolated from generated code. The implementation receives inputs and returns constrained outputs; trusted code computes metrics and the final comparison outside its writable environment.
FR-26 · P0  Correctness and comparability checks shall precede performance comparisons. The evaluator shall reject missing outputs, NaN or infinite values, invalid shapes, altered data, and failing reference tests. A numeric match alone shall not imply method fidelity.
FR-27 · P0  Measurement shall follow the frozen specification. Runtime studies shall record warm-up, repetition count, ordering, hardware, thread settings, and measurement boundaries. Timing overhead must be measured or held comparable; untrusted self-reported timing is insufficient.
FR-28 · P0  For a runtime reduction, the harness shall subtract proposed runtime from baseline runtime, divide that difference by baseline runtime, and multiply by 100, using the specified aggregation. It shall reject nonpositive baselines. Accuracy differences shall distinguish percentage points from relative percentages.
FR-29 · P0  Stochastic experiments shall retain all seed-level results and report the declared summary and uncertainty estimate. A single observation or overlapping confidence intervals shall not automatically establish equivalence.
FR-30 · P0  The deterministic decision engine shall apply the following ordered rules. An LLM may explain the outcome but shall not override it.
Condition in order
Assessment

FR-31 · P0  For an equivalence-style check, an agreed confidence interval fully inside the acceptance band may pass, fully outside may fail, and partial overlap is inconclusive. Other claim types require their own reviewed rule. Descriptive checks without uncertainty shall be labeled accordingly.
FR-32 · P0  The report shall state that failure to reproduce is not proof that a paper is false. Remaining implementation errors, environmental differences, and incomplete specifications shall be listed when relevant.

These are logical roles, not a requirement for six simultaneous agents or six models. A sequential implementation is preferred for the MVP. Only the orchestrator may authorize tools. Model outputs must validate against schemas; invalid output gets one constrained retry, counted against the global budget.
State transitions
Document state: uploaded → extracting → ready, needs_review, or rejected. Experiment state: draft → needs_information or ready. A ready experiment is immutable for a particular run; edits create a new version.
Run state: queued → planning → generating → testing → executing → evaluating → completed. A test or execution failure may enter repairing and return to testing if repair and time budgets remain. Terminal alternatives are failed, canceled, or budget_exceeded. “Inconclusive” is an assessment, not a process state.
OR-01 · P0  Every transition shall persist its event, timestamp, reason, and current attempt. The system shall reject invalid transitions and terminal-state rewrites. Transition events shall be monotonically sequenced per run.
OR-02 · P0  A worker shall acquire a renewable lease. On a lost lease, another worker shall first reconcile the runner using the run ID before restarting. At-least-once queue delivery shall not duplicate an active experiment.
OR-03 · P0  Transient provider errors may receive at most two exponential-backoff retries within the remaining budget. Policy blocks, invalid credentials, and unavailable models shall fail clearly; no silent provider or model fallback is allowed.
OR-04 · P0  Prompt-injection text in papers, repositories, logs, or dataset metadata shall be treated as data. It shall never expand tool permissions, change budgets, modify evaluator rules, or authorize network access.
Model provenance
Record provider, exact model identifier, sampling settings, prompt-template version, input hashes, token usage, and request IDs when available. Raw model exchanges are private artifacts subject to redaction and retention. Model nondeterminism means identical seeds do not guarantee identical regenerated code; execution reruns should use the frozen code snapshot.

DATA-01 · P0  Foreign keys shall enforce ownership and lineage. Unique constraints shall cover claim version, experiment version, per-run event sequence, and idempotency scope. Published run snapshots shall be append-only.
DATA-02 · P0  Artifact keys shall be generated by the server. User-provided filenames shall not become filesystem paths. Hash validation shall detect missing or altered artifacts before export and rerun.
DATA-03 · P0  Postgres shall own durable state and metadata; Redis shall carry disposable queue and progress data. Redis loss shall not erase specifications or completed results. Large logs, PDFs, datasets, and code snapshots belong in the artifact store.
DATA-04 · P0  Every artifact shall distinguish trusted supervisor output, evaluator output, generated code output, and model narrative. Hashes establish byte identity, not scientific validity or independent attestation.
Default retention is 30 days after the last project activity. User deletion revokes access immediately and removes active artifacts within 24 hours. Backups expire within 7 days; restoration must replay deletion tombstones before serving traffic. Retention settings and deletion status shall be visible.

Error and concurrency behavior
Errors shall contain code, message, details, request_id, and retryable. Use 400 for malformed input, 401/403 for access failures, 404 for unavailable resources, 409 for version or state conflicts, 413 for oversized uploads, 422 for unsupported or incomplete specifications, and 429 for quotas. No stack trace or secret appears in client errors.
Runner interface
The internal runner accepts run_id, attempt_id, image digest, input artifact digests, approved entrypoint, resource limits, and an output schema. It returns a runner job ID and trusted telemetry. It shall not accept arbitrary host mount paths, Docker flags, privileged mode, or a shell command from the public API.
Model interface
The provider adapter exposes structured generation and permitted tool calls. It normalizes provider failures and usage. Secrets stay in the control plane; model responses are parsed and validated before any filesystem or runner operation. Model selection is configuration, not a hard-coded assumption about future availability.

13 Security privacy and trust boundaries
SEC-01 · P0  The private MVP shall use authenticated access and owner checks on every project, report, artifact, export, and event stream. Public multi-user deployment requires an additional isolation review before launch.
SEC-02 · P0  Generated code shall run in rootless containers on a dedicated disposable VM, with read-only root filesystem, no-new-privileges, dropped Linux capabilities, resource limits, and default-deny network access. Containers alone shall not be described as a complete hostile-code security boundary.
SEC-03 · P0  No Docker socket, cloud credentials, model key, host home directory, database credential, or unrestricted host volume shall be mounted into an experiment. The evaluator and control plane shall execute outside the writable sandbox.
SEC-04 · P0  A restricted data broker shall permit only approved HTTPS sources and validate redirects and resolved addresses. It shall block loopback, link-local, private and cloud metadata endpoints. The MVP can avoid URL fetching entirely by preloading datasets.
SEC-05 · P0  The trusted evaluator shall validate outputs as bounded JSON or numeric arrays. It shall not deserialize pickle or execute generated report scripts. Hidden correctness inputs may detect hard-coded answers, but do not establish general algorithm correctness.
SEC-06 · P0  API keys shall be injected through server-side secret configuration and redacted from logs. TLS shall protect deployed traffic. Storage shall use host or provider encryption at rest and least-privilege service identities.
SEC-07 · P0  Before upload, the UI shall disclose that relevant paper content may be sent to the configured model provider. Private papers shall not be used for training by Paper2Proof. Provider retention behavior must be checked separately and shall not be promised without verification.
SEC-08 · P0  Generated code, imported dependencies, and dataset archives shall undergo policy and integrity checks. Static scanning is advisory; runtime isolation remains mandatory even when scans pass.
SEC-09 · P0  Export and download handlers shall enforce ownership, safe filenames, MIME types, and attachment disposition. HTML reports shall use a restrictive content-security policy and escaped content.
Residual limitations
A protected evaluator reduces accidental or deliberate metric manipulation, but cannot guarantee that an implementation faithfully follows a paper. Domain correctness tests, source review, and explicit uncertainty remain necessary. The MVP is a research engineering assistant, not an independent scientific authority.

Three minute demonstration
0:00–0:30: Upload the selected paper and show its source-linked claim. 0:30–1:00: Inspect conditions, baseline, budget, and assumptions. 1:00–2:00: Show generated code, real execution events, and evaluator checks. 2:00–2:40: Open measurements, verdict rationale, and downloadable evidence. 2:40–3:00: Show an incomplete claim correctly labeled inconclusive.
If execution takes longer than the presentation, use an accurately labeled recording or a completed run with timestamps and a separate live short fixture. Never imply a precomputed result was generated live.
Release package
The submission should include the working private demo, source repository, setup instructions, short demo video, two or three supported-paper examples, acceptance-test evidence, third-party attribution, and a clear explanation of newly implemented features. Exact submission requirements must be confirmed from the event organizers.
Proposed repository organization
Use apps/web for the UI; services/api and services/worker for control and orchestration; packages/contracts for schemas; packages/evaluation for trusted adapters; runners/ for isolated execution definitions; third_party/ for retained upstream components; tests/fixtures for reviewed examples; and docs/ for architecture, limitations, and source attribution.

Definition of done
Paper2Proof is ready for the MVP demonstration when one supported real-paper claim completes end to end with traceable measurements, an incomplete case returns an honest inconclusive assessment, exported evidence can be rerun, every P0 acceptance check passes, and attribution and known limitations are documented.
